# Theme Manager Documentation

## 1. Executive Summary

The `ThemeManager` (`src/ui/managers/theme_manager.py`) is the central component responsible for defining, managing, and applying the visual theme across the application's user interface. It ensures a consistent look and feel by providing theme-specific color palettes and dynamically generating Qt Style Sheets (QSS). This manager supports dynamic theme switching (light/dark mode) and integrates with application settings for user preferences.

## 2. Core Concepts

### `Theme` Dataclass
The `Theme` dataclass (`src/ui/managers/theme_manager.py`) is a blueprint for a visual theme. It encapsulates all the necessary color definitions (e.g., `background`, `text`, `accent`, `danger`, `color_good`, `color_bad`) that constitute a theme's palette.

```python
@dataclass
class Theme:
    """Holds all the color and metric data for a UI theme."""
    name: str

    # Palette
    background: str = "#F0F0F0"
    text: str = "#000000"
    accent: str = "#0078D7"
    danger: str = "#C50F1F"
    # ... and many more color attributes
```

### Pre-defined Themes
The `ThemeManager` includes two default theme instances:
-   `DEFAULT_LIGHT`: A light-colored theme.
-   `DEFAULT_DARK`: A dark-colored theme with an adjusted palette for better readability.

### `get_theme(name: str) -> Theme`
This method retrieves a `Theme` object by its string name (e.g., "light", "dark"). It provides a fallback to `DEFAULT_LIGHT` if the requested theme name is not found.

### `generate_stylesheet(theme: Theme, font_family: str, font_size: int) -> str`
This is the most critical method. It takes a `Theme` object and font settings to dynamically create a comprehensive QSS string. This QSS string is then applied to the application (typically by the main `UIManager`), styling the majority of the UI elements according to the selected theme. It includes dynamic calculations for element sizes (e.g., `groupbox_margin_top`, `subject_font_size`) to ensure proper scaling with font settings.

## 3. How Themes are Applied and Accessed

The application utilizes a multi-pronged approach to apply theming, combining global stylesheets with more granular, context-specific color application.

### 3.1. Global Styling via Stylesheet Generation

The primary method for theming is through a global stylesheet applied at the application's root level. This process is managed within `src/app/application.py`.

1.  **Instantiation**: In the `ApplicationWindow.__init__` method, the `ThemeManager` is created.
2.  **Initial Application**: A helper function, `apply_theme`, is immediately called. This function performs the core logic:
    *   Retrieves the current theme name and font settings from the `SettingsManager`.
    *   Gets the corresponding `Theme` object from the `ThemeManager`.
    *   Calls `theme_manager.generate_stylesheet()` to create the complete QSS string.
    *   Applies the generated stylesheet to the global `QApplication` instance using `app.setStyleSheet()`.
3.  **Dynamic Updates**: The `ApplicationWindow` connects to the `settings_manager.signals.setting_changed` signal. If the `theme`, `font_family`, or `font_size` keys change, its `_on_setting_changed` slot calls `apply_theme` again to regenerate and re-apply the stylesheet, ensuring the entire UI updates to reflect the new settings.

This top-down approach means most widgets are styled "passively" by the global stylesheet, without needing to interact with the `ThemeManager` directly.

### 3.2. Semantic Styling via QSS Attribute Selectors

This pattern elegantly decouples application logic from visual presentation, particularly for data-driven statuses.

*   **Builder's Role**: Components like `build_preferences_view_model` (`src/ui/builders/preferences_view_model_builder.py`) process game data and assign *semantic status strings* (e.g., `"great"`, `"good"`, `"bad"`, `"warning"`) to elements within view models. These view models are then displayed by UI widgets.
    ```python
    # Example from build_preferences_view_model
    if score >= LOVES_THRESHOLD: status = "great"
    # ...
    ds_data.append({'label': labels[level], 'score': score, 'status': status})
    ```
*   **Stylesheet's Role**: The QSS generated by `ThemeManager` contains specific rules that target these semantic attributes, applying theme-appropriate colors.
    ```qss
    /* Example from theme_manager.py generate_stylesheet */
    QLabel#dsLabel[status="great"] {{ border-color: {theme.color_great}; color: {theme.color_great}; }}
    QLabel#dsLabel[status="good"] {{ border-color: {theme.color_good}; color: {theme.color_good}; }}
    ```
    This means the logic determines *what* a status is, and the `ThemeManager`'s QSS determines *how* that status is visually represented.

### 3.3. Direct Color Injection for Custom Widgets

For widgets with custom painting logic or specific needs that cannot be adequately addressed by a static stylesheet, presenters can directly query the `ThemeManager` for specific color values and pass them to the widgets.

An example is found in `TalentProfilePresenter` (`src/ui/presenters/talent_profile_presenter.py`):
1.  The presenter retrieves the active `Theme` object.
    ```python
    # src/ui/presenters/talent_profile_presenter.py
    current_theme_name = self.controller.settings_manager.get_setting("theme", "light")
    current_theme = self.controller.theme_manager.get_theme(current_theme_name)
    ```
2.  It then calls a method on specific child widgets (e.g., `preferences_widget`, `hiring_widget`), passing individual color values from the `Theme` object.
    ```python
    # src/ui/presenters/talent_profile_presenter.py
    self.view.preferences_widget.set_theme_colors(danger_color=current_theme.danger)
    self.view.hiring_widget.set_theme_colors(danger_color=current_theme.danger)
    ```
    This allows widgets with bespoke rendering to integrate seamlessly with the current theme.

## 4. Handling Dynamic Theme Changes

The application supports dynamic theme switching. When the user changes the "theme" or "font_size" setting, the UI needs to update. `TalentProfilePresenter` demonstrates this reactive behavior for widgets that require direct color injection:

```python
# src/ui/presenters/talent_profile_presenter.py
@pyqtSlot(str)
def _on_setting_changed(self, key: str):
    if key == "theme" or key == "font_size":
        # 1. Re-fetch the current theme and potentially other settings
        current_theme_name = self.controller.settings_manager.get_setting("theme", "light")
        current_theme = self.controller.theme_manager.get_theme(current_theme_name)
        
        # 2. Re-inject directly used colors to relevant widgets
        self.view.preferences_widget.set_theme_colors(danger_color=current_theme.danger)
        self.view.hiring_widget.set_theme_colors(danger_color=current_theme.danger)
        
        # 3. Reload the view's data, which will trigger UI updates
        # (The global stylesheet is updated separately by ApplicationWindow)
        self._load_data_for_current_talent()
```
This ensures that both directly injected colors and globally applied QSS styles are refreshed to reflect the new theme or font size.

## 5. Key Files

*   `src/app/application.py`: Manages the instantiation and global application of the theme via the `ApplicationWindow` class.
*   `src/ui/managers/theme_manager.py`: Contains the `Theme` dataclass, default theme definitions, and the logic for retrieving themes and generating QSS.
*   `src/ui/presenters/talent_profile_presenter.py`: Demonstrates direct color injection and reaction to theme setting changes.
*   `src/ui/builders/preferences_view_model_builder.py`: Shows how semantic status strings are assigned to data, which are then picked up by the QSS.
*   `src/ui/widgets/talent_profile/details_widget.py`: An example of a widget that is primarily styled via the global QSS.
*   `src/ui/view_models.py`: Defines dataclasses for UI data, some of which might contain `status` or `color` fields that interact with the theming system.
